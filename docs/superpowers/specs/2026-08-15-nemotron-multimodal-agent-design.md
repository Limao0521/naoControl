# Nemotron Multimodal Agent for NAO

**Date:** 2026-08-15

**Status:** Approved design, pending implementation plan

**Target:** NAO V6 with NAOqi 2.8, a Python 3 PC gateway, and NVIDIA-hosted Nemotron services

## 1. Purpose

Replace the current Groq-based conversation subsystem with a Nemotron-based multimodal agent. The robot remains the physical execution environment; the PC becomes the trusted agent host and policy boundary; NVIDIA cloud services perform speech recognition, visual understanding, and language-model reasoning.

The system must let a person:

1. boot NAO Control into its existing web-control mode with all Nemotron API calls disabled;
2. enter or leave intelligent mode using the left foot bumper;
3. hold the right foot bumper to speak and release it to submit the interaction;
4. ask questions that depend on what NAO is seeing at the same time;
5. receive a spoken response and, when appropriate, see NAO execute safe NAOqi actions selected through a typed tool interface;
6. stop physical activity locally even if the PC, network, or cloud is unavailable.

## 2. Design principles

1. **NAO is the body, not the cloud client.** NAO runs only the Python 2.7/NAOqi adapter, safety supervisor, mode controller, sensor relay, and action executor.
2. **The PC is the trust boundary.** It owns API credentials, session memory, sensor synchronization, model orchestration, MCP, policy validation, and logs.
3. **Nemotron never calls NAOqi directly.** Model tool calls are requests, not commands. They pass through the MCP server, policy engine, and a second validator on the robot.
4. **No cloud traffic in web-control mode.** Entering intelligent mode permits cloud use; releasing the push-to-talk bumper creates a cloud interaction.
5. **Physical safety is deterministic.** Emergency stop, movement timeouts, posture checks, and actuator limits do not depend on an LLM response.
6. **Perception is interaction-scoped.** Audio, images, robot state, model decisions, tool calls, and execution results share an immutable `interaction_id`.
7. **Migration is explicit.** The Groq/Gemini/OpenAI conversation implementation is removed after the Nemotron path passes acceptance tests; it is not kept as an unmaintained parallel runtime.

## 3. Scope

### 3.1 In scope

- Web Control and Nemotron mode management.
- Left-bumper mode switching and right-bumper push-to-talk.
- A local emergency gesture using both bumpers.
- Audio relay from NAO to the PC.
- A local camera ring buffer and interaction-specific frame selection.
- Robot-state snapshots synchronized with user interactions.
- NVIDIA speech recognition, visual perception, and Nemotron reasoning clients.
- A PC-hosted, MCP-compatible capability server.
- Typed action schemas, policy validation, action execution, acknowledgements, cancellation, and timeouts.
- Native NAO TTS for the first release.
- Clear status indication through eye LEDs.
- Removal of versioned API credentials and insecure TLS behavior.
- Automated tests that can run without a physical robot plus a supervised hardware test protocol.

### 3.2 Out of scope for the first release

- Full-duplex speech or barge-in while NAO is speaking.
- Continuous cloud upload of ambient audio or video.
- Autonomous navigation or unrestricted walking.
- Arbitrary joint trajectories generated by the model.
- Runtime installation of third-party behavior packages.
- Recognition of the spoken wake word "NAO".
- Model fine-tuning.
- Replacing the existing web frontend.
- Replacing NAOqi with LoLA, OAN, ROS 2, or a RoboCup framework.

## 4. System context

The existing repository provides:

- a Python 2.7 WebSocket control server on port 6671;
- `NAOFacade`, `CommandFactory`, command classes, and a movement watchdog;
- 52 registered actions;
- camera streaming based on `ALVideoDevice`;
- bumper polling and event examples;
- native TTS, LEDs, behavior execution, posture, motion, recording, and state queries;
- a React web-control client.

The current conversation loop records fixed five-second WAV files on the robot, calls Groq Whisper and an LLM from Python 2.7, and sends only text to NAO TTS. It has no wake word, VAD, streaming, multimodal synchronization, tool calling, or safe agent action layer. This subsystem will be replaced.

## 5. Target architecture

```text
+----------------------- NAO V6 -----------------------+
| Mode Manager  Sensor Bridge  Action Executor         |
| Safety Supervisor  NAOFacade  CommandFactory         |
|       | audio/images/state/events | actions/acks      |
+-------+---------------------------+-------------------+
        | authenticated local WebSocket channels
+-------+---------------------------+-------------------+
|                     PC Gateway                        |
| Sensor Hub       Interaction Manager       Memory    |
| NVIDIA Clients   Nemotron Agent Host        MCP      |
| Policy Engine    Robot Client               Audit    |
+-------+---------------------------+-------------------+
        | HTTPS/TLS, credentials only on PC
+-------+---------------------------+-------------------+
|                  NVIDIA Cloud                         |
| Nemotron ASR   Nemotron vision/omni   Nemotron agent |
+-------------------------------------------------------+
```

### 5.1 Robot responsibilities

- Publish bumper transitions and the current operating mode.
- Stream camera and microphone data only when requested by the current mode.
- Publish state and safety telemetry.
- Validate and execute a restricted command envelope.
- Preempt actions on emergency stop or timeout.
- Return structured acknowledgements and results.
- Maintain a safe state when the PC disconnects.

### 5.2 PC responsibilities

- Authenticate the robot and reject other command clients.
- Own the operating session and API-call gate.
- Synchronize audio, frames, and robot state.
- Call ASR, visual perception, and agent models.
- Maintain summarized conversation history.
- Expose MCP resources and tools.
- Validate model-generated tool calls.
- Serialize body actions and manage cancellation.
- Record audit events without storing secrets or unnecessary raw media.

### 5.3 Cloud responsibilities

- Transcribe interaction audio in Spanish.
- Convert selected camera frames into a structured visual observation.
- Generate a short Spanish response and zero or more typed tool calls.

The cloud is not an authority for safety, identity, mode selection, or direct motion.

## 6. Operating modes and bumper contract

### 6.1 Bumper mapping

| Input | Context | Result |
|---|---|---|
| Hold left bumper for 1.5 seconds | `WEB_CONTROL` | Request entry into `NEMOTRON_READY` |
| Hold left bumper for 1.5 seconds | Any non-emergency Nemotron state | Cancel work, stop actions, return to `WEB_CONTROL` |
| Press and hold right bumper | `NEMOTRON_READY` | Start interaction capture |
| Release right bumper | `CAPTURING` | Close capture and begin processing |
| Press both bumpers within 250 ms | Any state | Enter `EMERGENCY`, cancel cloud work, stop motion and behaviors |

The hold interval prevents accidental mode changes caused by ordinary foot contact. The right bumper has no recording-system function outside Nemotron mode. Existing independent bumper monitors must be consolidated so that only the Mode Manager interprets bumper transitions.

### 6.2 State machine

```text
BOOT
  -> WEB_CONTROL

WEB_CONTROL
  -- left hold and entry checks pass --> NEMOTRON_READY

NEMOTRON_READY
  -- right down --> CAPTURING
  -- left hold --> WEB_CONTROL

CAPTURING
  -- right up with valid audio --> PROCESSING
  -- cancellation/error --> NEMOTRON_READY

PROCESSING
  -- speech only --> SPEAKING
  -- approved tools --> ACTING
  -- timeout/error --> NEMOTRON_READY

ACTING
  -- tools complete --> SPEAKING or NEMOTRON_READY
  -- cancellation/timeout --> NEMOTRON_READY

SPEAKING
  -- TTS complete --> NEMOTRON_READY

ANY
  -- both bumpers --> EMERGENCY

EMERGENCY
  -- explicit manual reset and health checks --> WEB_CONTROL
```

### 6.3 Entry checks

Entry into intelligent mode requires:

- an authenticated and healthy PC gateway connection;
- no current locomotion or running behavior;
- a known posture, initially `StandInit`;
- Fall Manager enabled;
- battery at or above 30 percent;
- the emergency input and movement watchdog functioning;
- required NAOqi proxies available;
- NVIDIA service health confirmed or an explicitly configured local fallback.

Failure leaves the robot in Web Control and reports a structured reason.

### 6.4 LED states

| State | Face LED color |
|---|---|
| Web Control | Blue |
| Nemotron ready | Purple |
| Capturing | Cyan |
| Processing | Yellow |
| Acting | Green |
| Recoverable error | Red |
| Emergency | Flashing red |

LED commands generated by the model cannot override emergency or system-state indicators.

## 7. Interaction and sensor synchronization

### 7.1 Interaction lifecycle

When the right bumper is pressed, the PC creates an immutable UUID `interaction_id`. It records:

- press and release timestamps based on a shared monotonic timeline;
- audio with 250 ms pre-roll and 300 ms post-roll when available;
- a camera frame immediately before the press;
- one or more frames during the utterance;
- a frame at release;
- robot-state snapshots at press and release;
- the conversation session identifier.

Only releasing the right bumper can submit an interaction to cloud services.

### 7.2 Interaction envelope

```json
{
  "protocol_version": "1.0",
  "interaction_id": "4b089699-dbc3-4e46-80e5-380122c74f52",
  "session_id": "6f0c0b52-a55b-4f53-9dad-86d3a89738db",
  "started_at_ms": 1786840123124,
  "ended_at_ms": 1786840127531,
  "audio": {
    "encoding": "pcm_s16le",
    "sample_rate_hz": 16000,
    "channels": 1,
    "duration_ms": 4407
  },
  "frames": [
    {"frame_id": "before", "captured_at_ms": 1786840122910},
    {"frame_id": "middle", "captured_at_ms": 1786840125150},
    {"frame_id": "release", "captured_at_ms": 1786840127490}
  ],
  "robot_state": {
    "posture": "StandInit",
    "battery_percent": 72,
    "fallen": false,
    "fall_manager_enabled": true,
    "running_behavior": null
  }
}
```

### 7.3 Camera policy

- The PC keeps a five-second local JPEG ring buffer while Nemotron mode is active.
- The default frame size is 640x480 with JPEG quality chosen to keep each frame below the configured request limit.
- At most three frames are sent for a normal interaction.
- A question requiring temporal reasoning may select additional frames up to a hard configured maximum.
- Web Control may continue to use its existing local video stream independently, but Web Control frames are not uploaded to cloud services.
- Raw frames expire from the ring buffer unless audit media retention is explicitly enabled for a test session.

### 7.4 Audio policy

- The robot relays mono 16 kHz PCM to the PC during push-to-talk.
- Audio is not streamed to NVIDIA before the bumper release.
- TTS and microphone capture are mutually exclusive in the first release.
- Maximum utterance length is 20 seconds; reaching the limit closes the capture and reports it to the user.
- Empty, clipped, or inaudible captures return to `NEMOTRON_READY` without calling the agent.

## 8. Nemotron pipeline

### 8.1 Model roles

1. **Speech:** a NVIDIA Nemotron/Riva streaming-capable multilingual ASR model transcribes Spanish audio.
2. **Vision:** Nemotron 3 Nano Omni or Nemotron Nano VL converts selected images into a constrained visual observation.
3. **Agent:** Nemotron 3 Nano 30B-A3B receives the Spanish transcript, visual observation, robot state, conversation summary, and tool schemas.

The visual models currently document English-only language support. Therefore, the Vision Client prompts them in English and requires a language-neutral JSON observation. The multilingual Agent converts that observation into a Spanish response.

### 8.2 Visual observation contract

```json
{
  "scene_summary": "A red bottle is centered on a table in front of the robot.",
  "objects": [
    {
      "label": "bottle",
      "color": "red",
      "position": "center",
      "confidence": 0.91
    }
  ],
  "people": 1,
  "uncertainties": []
}
```

Vision output is untrusted model data. It is context for conversation and never proves that a motion path is physically clear. Navigation and collision safety require deterministic sensors and are outside the first release.

### 8.3 Agent output

The Agent Host uses the OpenAI-compatible tool-calling interface. A model response may contain:

- Spanish speech text;
- zero or more typed tool calls;
- no executable code, shell text, filesystem paths, NAOqi method names, or arbitrary behavior names.

Reasoning content is not sent to TTS and is not required for audit storage.

### 8.4 Timeouts and retry policy

| Operation | Timeout | Retries |
|---|---:|---:|
| ASR | 12 s | 1 if no response body was received |
| Vision | 12 s | 1 if no response body was received |
| Agent | 15 s | 1 if no response body was received |
| Individual low-risk tool | 5 s | 0 |
| Behavior | Per registry, maximum 15 s | 0 |
| Full interaction | 35 s | Not applicable |

Retries reuse the same idempotency key. A network timeout never retries a physical tool execution automatically.

## 9. MCP-compatible capability server

### 9.1 Host arrangement

The PC runs both:

- a **Nemotron Agent Host**, which calls the NVIDIA endpoint and executes the agent loop; and
- a **NAO MCP Server**, which exposes the robot's approved resources and tools.

Nemotron does not independently connect to MCP. The Agent Host is the MCP client and the only model-facing orchestrator.

### 9.2 Resources

```text
nao://state
nao://camera/latest
nao://camera/interactions/{interaction_id}
nao://behaviors
nao://capabilities
nao://sessions/{session_id}
```

Resources return structured data and never expose robot filesystem paths or credentials.

### 9.3 First-release tools

#### Safety and observation

```text
get_robot_state()
capture_image(camera)
stop_all()
```

#### Speech and expression

```text
say(text, language="Spanish")
set_led(group, color, duration_seconds)
play_sound(asset_id)
```

#### Body actions

```text
look(direction, speed)
set_posture(posture, speed)
gesture(gesture_id, intensity)
run_behavior(behavior_id)
```

`turn` and `walk_short` are specified for a later release and are not exposed until motion acceptance tests pass.

### 9.4 Explicitly prohibited model tools

- Generic joint movement.
- Raw `moveTo` coordinates.
- Arbitrary stiffness changes.
- Disabling Fall Manager.
- Arbitrary WebSocket action forwarding.
- Dynamic imports, Python execution, shell execution, network requests, or file access.
- Behavior discovery by substring at execution time.
- Model control of recording, logging, API credentials, mode transitions, or emergency reset.

## 10. Action registry and policy engine

### 10.1 Registry record

```json
{
  "name": "run_behavior",
  "risk": "medium",
  "timeout_seconds": 12,
  "exclusive_resource": "body",
  "cancelable": true,
  "preconditions": {
    "allowed_modes": ["NEMOTRON_READY", "ACTING"],
    "allowed_postures": ["Stand", "StandInit"],
    "minimum_battery_percent": 30,
    "fall_manager_required": true,
    "fallen": false
  },
  "parameters": {
    "behavior_id": {
      "type": "string",
      "enum": ["wave", "disco", "kick", "siu"]
    }
  }
}
```

### 10.2 Validation sequence

1. Parse tool call against strict JSON Schema with unknown fields rejected.
2. Confirm the tool and arguments appear in the versioned Action Registry.
3. Check current mode and interaction ownership.
4. Query fresh robot state.
5. Check battery, posture, Fall Manager, fallen state, and resource locks.
6. Enforce per-turn limits: at most three tool calls and one body action.
7. Convert semantic tool arguments into a versioned robot command envelope.
8. Send the command with a unique `command_id`.
9. Require an acknowledgement before continuing.
10. Record result or timeout and restore the expected posture when configured.

The robot repeats all safety-relevant checks before execution.

### 10.3 Concurrency

- Only one interaction may own the body at a time.
- TTS may not overlap microphone capture.
- LED state indicators have higher priority than agent LED requests.
- `stop_all` bypasses the normal queue.
- Leaving Nemotron mode cancels queued tools and active model calls.

## 11. PC-to-robot protocol

The existing WebSocket transport remains, but the agent channel requires a versioned envelope and authentication. Web-control commands and gateway commands must have separate authorization roles.

### 11.1 Command envelope

```json
{
  "protocol_version": "1.0",
  "message_type": "command",
  "command_id": "e1920e79-49be-458d-b654-23c8f4379ec2",
  "interaction_id": "4b089699-dbc3-4e46-80e5-380122c74f52",
  "issued_at_ms": 1786840129000,
  "expires_at_ms": 1786840134000,
  "action": "set_led",
  "arguments": {
    "group": "eyes",
    "color": "red",
    "duration_seconds": 1.0
  }
}
```

### 11.2 Acknowledgement envelope

```json
{
  "protocol_version": "1.0",
  "message_type": "command_result",
  "command_id": "e1920e79-49be-458d-b654-23c8f4379ec2",
  "interaction_id": "4b089699-dbc3-4e46-80e5-380122c74f52",
  "status": "completed",
  "started_at_ms": 1786840129050,
  "ended_at_ms": 1786840129460,
  "result": {}
}
```

Valid statuses are `accepted`, `rejected`, `running`, `completed`, `cancelled`, `timed_out`, and `failed`.

### 11.3 Authentication

- The gateway uses a per-installation secret provisioned outside Git.
- Every privileged message is authenticated; replayed, expired, or malformed messages are rejected.
- Port 6671 is restricted to the trusted PC on the robot network.
- Cloud credentials never transit to or reside on NAO.
- TLS certificate verification remains enabled for every NVIDIA request.

The exact local-channel mechanism will be chosen in the implementation plan based on libraries that remain compatible with Python 2.7. The security properties above are requirements, not optional implementation ideas.

## 12. Safety behavior

### 12.1 Emergency stop

Both bumpers pressed within 250 ms must locally:

1. set mode to `EMERGENCY`;
2. stop locomotion;
3. stop all behaviors;
4. cancel queued commands;
5. signal the PC to cancel active model calls;
6. flash the face LEDs red;
7. require an explicit manual reset after health checks.

The emergency path must not wait for the WebSocket event loop, MCP, or cloud.

### 12.2 Disconnect behavior

If the PC heartbeat is lost for more than two seconds in a Nemotron state:

- active locomotion and behaviors stop;
- new push-to-talk interactions are rejected;
- the robot returns to Web Control only after the local action queue is safe;
- the error is indicated in red and logged.

### 12.3 Content and privacy

- The microphone and camera are uploaded only for a user-initiated interaction.
- Logs store hashes and metadata by default, not raw audio or images.
- Test-media retention is opt-in, bounded, and visibly indicated.
- Agent speech is length-limited and sanitized for NAO TTS.
- Model text cannot alter mode, safety policy, authentication, or tool definitions.

## 13. Error handling

| Failure | Required behavior |
|---|---|
| PC unavailable on mode entry | Remain in Web Control and report gateway unavailable |
| NVIDIA unavailable | Return to Nemotron Ready; do not execute tools |
| ASR returns no speech | Brief local indication; no Agent call |
| Vision fails | Continue only if the question does not require vision; otherwise explain uncertainty |
| Invalid tool call | Reject, return structured tool error to Agent, never forward to NAO |
| Action precondition fails | Reject and explain the current constraint |
| Robot acknowledgement timeout | Call local `stop_all`, mark interaction failed |
| Bumper release event missing | Close audio at the 20-second hard limit |
| Mode exit during processing | Cancel requests and discard pending tool calls |
| Mode exit during acting | Stop current action before returning to Web Control |

## 14. Migration from the current conversation subsystem

### Phase 0: repository safety

- Revoke and rotate every committed Groq and Gemini credential.
- Remove credentials and fallback secrets from tracked files and history.
- Replace secret configuration with documented environment variables or local secret files excluded by Git.
- Remove TLS bypasses.
- Add secret-scanning checks.

### Phase 1: mode and protocol foundation

- Introduce a single Mode Manager.
- Consolidate bumper ownership.
- Add authenticated gateway role, command envelopes, acknowledgements, and heartbeats.
- Preserve current Web Control behavior.

### Phase 2: sensor gateway

- Implement audio relay and camera ring buffer.
- Add synchronized state snapshots and interaction envelopes.
- Validate capture without cloud calls.

### Phase 3: Nemotron shadow mode

- Add ASR, vision, and agent clients on the PC.
- Generate responses and tool calls without executing them.
- Measure latency, transcript quality, visual grounding, and tool validity.

### Phase 4: low-risk actions

- Enable state queries, speech, and LEDs.
- Add native TTS lifecycle handling.

### Phase 5: body actions

- Enable look, posture, gestures, and reviewed behaviors.
- Require simulation and supervised physical tests for each Action Registry entry.

### Phase 6: removal

- Remove `nao_conversation.py`, the Groq/Gemini/OpenAI providers, Whisper/Groq STT, and conversation WebSocket commands.
- Update deployment manifests and documentation.
- Retain no hidden fallback to the old conversation subsystem.

## 16. Testing strategy

### 16.1 Unit tests

- State-machine transitions and invalid events.
- Bumper debounce, hold duration, simultaneous emergency detection, and missing release.
- Protocol serialization, validation, expiry, replay rejection, and authentication.
- Interaction audio/frame/state alignment.
- Action Registry schema and precondition checks.
- Tool-call parsing with unknown fields and adversarial values.
- Timeout, cancellation, and idempotency behavior.
- Secret configuration and TLS verification.

### 16.2 Contract tests

- PC gateway against a fake robot WebSocket server.
- Robot command server against recorded gateway envelopes.
- Nemotron clients against deterministic HTTP fixtures.
- MCP resource and tool schemas.
- Frontend behavior while transitioning between Web Control and Nemotron ownership.

### 16.3 Simulation tests

- Validate postures, gestures, and imported behaviors in qiBullet or the closest available simulator.
- Verify that only one body action can run.
- Verify stop and timeout paths.

Simulation is a screening step, not evidence of physical safety.

### 16.4 Supervised robot tests

- Robot secured in a clear 1.5 m x 1.5 m area.
- Battery above 30 percent and Fall Manager enabled.
- Every action first executed at reduced speed.
- An operator remains beside the robot with emergency access.
- Test both bumpers, PC disconnect, Wi-Fi loss, cloud timeout, malformed tool calls, action timeout, and shutdown.

### 16.5 Multimodal evaluation

- At least ten Spanish speakers representative of the intended audience.
- Quiet and event-noise conditions.
- Questions involving object identity, color, count, direction, and uncertainty.
- Measure Spanish word error rate, visual answer accuracy, invalid-tool rate, rejected-action rate, and end-to-end latency.

## 17. Acceptance criteria

### Mode and privacy

- Startup always enters Web Control.
- Web Control produces zero NVIDIA API requests.
- Left-bumper hold reliably enters and exits Nemotron mode without accidental toggles.
- Right-bumper push-to-talk cannot start outside Nemotron Ready.

### Safety

- 100 percent of tool calls outside the schema are rejected.
- Emergency stop remains local and preempts body actions.
- Cloud or PC failure never leaves an unbounded motor command active.
- The Agent cannot disable Fall Manager or modify stiffness.

### Interaction

- Audio, selected images, state, decisions, and actions share one `interaction_id`.
- NAO does not capture itself while speaking.
- Questions grounded in the selected camera frames are answered with explicit uncertainty when perception is ambiguous.
- P95 release-to-first-spoken-audio is below 2.5 seconds in the target demonstration network, or the measured limitation is documented before release approval.

### Engineering

- PC gateway tests, Python 2 compatibility checks, frontend tests, lint, and build pass.
- No API credentials or raw authorization tokens are tracked or logged.
- Installation and rollback are documented and reproducible.
- Every enabled behavior has recorded provenance, license, expected posture, timeout, and physical test status.

## 19. Confirmed decisions

- The current client-server control architecture is retained as the NAO transport and execution foundation.
- The current Groq-based conversation path is replaced rather than extended.
- The MCP-compatible server runs on the PC.
- Nemotron mode is disabled at startup.
- Left bumper selects mode; right bumper is hold-to-talk; both bumpers are emergency stop.
- Audio, camera, and robot state are synchronized per interaction.
- Native NAO TTS is used first.
- Walking and unrestricted joint motion are excluded from the first action catalog.
- Changes are developed on a branch from `main`, committed in reviewable units, and not pushed before implementation and testing are complete.
